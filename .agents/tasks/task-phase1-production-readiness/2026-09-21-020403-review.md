# Phase 1 production-readiness: runtime hook repair, AST resolution, and honest docs (v1)

Phase 1 turns two silently-broken capabilities into working ones and brings the documentation back in line with reality. The headline fix is the Python automatic runtime hook: `sys.settrace` was installed but captured zero events because the frame filter classified all user code (module `__main__`) as standard library and excluded any module whose name merely contained `"tracer"`. The filter is reworked to decide user-vs-stdlib by source-file location and to exclude the tracer by its own `__file__`. Alongside it, `get_containing_function` in the Rust core (which always returned `None`) now walks the tree-sitter parent chain, binding-crate warnings are cleaned up, tests are added for both fixes, and a batch of status documents that had prematurely declared auto-tracing "complete" are corrected. No dependencies were added; `cargo test`, `cargo clippy -D warnings`, and the two Python correctness scripts all pass.

Watch for: (1) the central `sys.settrace` fix has no unit test of its own — `_should_trace`/`_is_stdlib_file` are only exercised through the `test_automatic_tracing.py` integration script, whose assertions are weak (`len(events) > 0`) — **confirmed**; (2) the `xplainit-python/README.md` bullet that this PR edited still claims auto-tracing captures "variable assignment, and control flow decision," but line-level tracing is a hard no-op (`_handle_line` returns `None` unconditionally) — **confirmed**; (3) a pre-existing depth-accounting asymmetry at the `max_depth` boundary is now reachable for the first time because user frames finally trace — **likely**, pre-existing so out of scope but worth noting.

**Verdict**: APPROVED

## High-level view

The runtime-hook repair is the substance of this phase and it is correct, not just test-passing. Stdlib exclusion is now driven by whether a frame's source file lives under `sys.prefix`/`site-packages`/the stdlib directory, with the old module-name list demoted to a fast-path fallback; `__main__` is explicitly user code; and the tracer excludes itself by real-path filename rather than by the substring `"tracer"`. A direct probe confirms user code in a real file is traced while the stdlib frames it calls into (`json.dumps` → `encoder.py`) are excluded — so exclusion is genuinely path-based, not an artifact of builtins lacking Python frames.

The AST `get_containing_function` fix descends to the smallest tree-sitter node covering a location and walks upward to the nearest named function-like node, with a C/C++ declarator descent for the grammars that nest the name. It resolves correctly for Python, JS, JS methods, Rust, and C, and returns `None` at module level.

The binding cleanup adds a crate-level `#![allow(clippy::useless_conversion)]` to silence a lint against pyo3-generated wrapper code. The allow is broader than strictly necessary — it does not mask any hand-written conversion today, but a crate-wide inner attribute will silence a future one.

Test coverage is the weak spot. The two new Rust tracer tests exercise the Rust event store, not the Python frame filter that was actually broken; the Python filter's only guard is an integration script with permissive assertions. The documentation edits are honest and self-correcting except for one reaffirmed capability claim about line-level tracing.

### The `sys.settrace` frame filter, reworked to trace by file location

The original filter had two independent defects that combined to capture nothing. `'__main__'` sat inside `_stdlib_prefixes`, so the top-level-module check excluded the very script the user runs; and the self-exclusion `'xplainit' in module_name or 'tracer' in module_name` was a substring test that would also drop any user module named, say, `request_tracer`. With user frames excluded, the `call`-event callback never returned a local trace function, so no `return`/`exception` events fired either.

The rewrite inverts the decision to be location-first. `_stdlib_locations()` collects the realpaths of `sys.prefix`/`base_prefix`/`exec_prefix`, `site-packages`/`dist-packages` entries on `sys.path`, and `dirname(os.__file__)`; `_is_stdlib_file` then treats any frame whose source file lives under one of those roots as non-user code. `__main__` is short-circuited to user code, and the old name list survives only as a fast-path fallback. Self-exclusion is now a realpath comparison against the tracer's own `__file__`, plus a precise `module_name == 'xplainit' or startswith('xplainit.')`, plus rejection of framel­ess files (`<string>`, `<frozen ...>`). Decisions are cached per `co_filename`, which is sound because a file's user-vs-stdlib status never changes.

A direct probe (user function in a real temp file calling `json.dumps`) confirms the behavior that matters: the user function produces enter+exit events while the stdlib frames it descends into produce none. That rules out the false-positive reading where Test 3's "0 stdlib events" is only because `len` and `os.path.basename` happen not to leave Python frames — path-based exclusion is doing real work.

```
frame ──▶ realpath(co_filename)
            │
            ├─ == tracer.__file__ ............... skip (no self-recursion)
            ├─ module xplainit[.*] .............. skip
            ├─ starts with '<' or empty ......... skip (interpreter internals)
            ├─ under sys.prefix/site-packages ... skip (stdlib/3rd-party)
            └─ else (incl. __main__) ............ TRACE
```

One pre-existing hazard becomes reachable now that user frames trace. Depth is incremented in `_handle_call` and decremented in `_handle_return`, but `_should_trace` bails when `depth > max_depth`. At the boundary, a frame's `call` can be counted while its `return` is filtered out (the depth is one higher at return time), so the per-thread depth can ratchet upward and eventually wedge tracing off for that thread. The depth-limiting test recurses 5 levels under `max_depth=3` and records 4 events — an imbalance consistent with this asymmetry — but only asserts `> 0`, so it neither catches nor rules out the drift. The handlers and the guard are unchanged from master, so this is out of scope for the PR, but it is the kind of thing that only surfaced because the filter finally works. Decrementing depth on return unconditionally would make the accounting symmetric.

### AST enclosing-function resolution via upward tree-sitter walk

`get_containing_function` previously delegated to a helper that, lacking parent links, always returned `None`. It now operates on the retained `Tree` directly: `smallest_node_at` recurses to the most specific node whose line range contains the location, then the caller walks `node.parent()` upward until it hits a function-like node and reads the name. `is_function_node` enumerates the relevant kinds per grammar (Python `function_definition`, the JS family including `method_definition` and `arrow_function`, Rust `function_item`, C/C++ sharing `function_definition`), and `function_name` reads the `name` field directly for the field-based grammars while `name_from_declarator` descends the C/C++ `declarator` chain to the identifier. Anonymous functions are skipped so resolution lands on the nearest *named* enclosing function.

The six new tests cover Python, JS, a JS method inside a class, Rust, C, and the module-level "returns `None`" case, and all pass. The one design limitation worth recording: `smallest_node_at` matches on line (row) only, ignoring column, and returns the first child whose line range contains the target. For a location on a line shared by multiple constructs the resolved node could be the wrong sibling. It doesn't affect the tested single-statement-per-line cases, and callers pass runtime line numbers, so it is a latent edge rather than a bug here — but a column-aware tie-break would make it robust for minified or densely-packed source. The retired `find_function_in_hierarchy` is gone; `find_node_at` remains as a public method still used by the `ast_parsing` example, so there is no dead code.

### Binding cleanup and the crate-level clippy allow

The pyo3 `get_explanations`/`print_explanations` methods gain explicit `#[pyo3(signature = (verbosity=None))]` attributes, the unused `AutoTracer::new` `backend` parameter is renamed to `_backend`, and an unused `HashMap` import is dropped from the Node crate — all warning elimination.

The crate-level `#![allow(clippy::useless_conversion)]` covers `PyErr -> PyErr` `.into()` calls that pyo3 0.22's `#[pymethods]`/`#[pyfunction]` macros generate in code the author doesn't control. There are no hand-written `.into()` calls in `lib.rs` today, so it masks nothing real now. The cost is scope: a crate-wide inner attribute will also silence a genuinely redundant conversion someone writes by hand later. A `#[allow]` on the specific `#[pymethods]` impls, or a comment pointing at the exact macro origin, would keep the lint useful for future hand-written code.

### Test coverage: the fix that mattered most is the least directly tested

The two new Rust tests — `test_record_events_flow_through_to_store` and `test_disabled_tracer_records_nothing` — verify that the Rust `PythonTracer` persists enter/exit events into the store when enabled and records nothing when disabled. They are meaningful for the Rust recording path and would fail if `record_function_*` stopped persisting. But they do not touch the Python `_should_trace`/`_is_stdlib_file` logic, which is where the actual FEAT-002 bug lived. That logic is guarded only by `test_automatic_tracing.py`, and its assertions are permissive: the basic and depth tests check `len(events) > 0`, which would pass even if enter/exit counts were badly skewed, and would still pass in several partial-revert scenarios. A handful of direct unit tests — a `__main__`/user file traces, a stdlib path does not, the tracer's own file does not, a user module containing the substring `tracer` still traces — would pin the fix against regression and encode the intended contract.

### Documentation corrected honestly, with one reaffirmed over-claim

The status-file edits are the good kind of documentation change: `OPTION2_POLISH_COMPLETE.md`, `PHASE2_COMPLETE.md`, and `IMPLEMENTATION_COMPLETE.md` each gain a "Correction" note stating plainly that auto-tracing had been declared complete prematurely and captured 0 events, and `CURRENT_STATUS_AND_NEXT_STEPS.md` / `PROGRESS.md` / `CHANGELOG.md` / `README.md` are updated to the now-working state with the specific root cause and the 3/3 test result. The README's "7 Rust examples" claim matches the actual `examples/` directory, and the new `real_world_debugging.rs` runs end to end through the `ErrorExplainer`.

The exception is the `xplainit-python/README.md` "Automatic Runtime Tracing" bullet, which this PR edited to append "Working as of the Phase 1 fix" while leaving the capability list as "every function call, variable assignment, and control flow decision." Auto-tracing emits call/return/exception events only; `_handle_line` returns `None` unconditionally, so variable assignments and control-flow decisions are not captured. Editing that line was the moment to correct the capability description, not reaffirm it. Trimming it to the events actually produced keeps the docs as honest as the rest of this phase.
