# Phase 4 production hardening: redaction, circuit-breaker, perf, and docs (v1)

Phase 4 hardens the framework across five fronts: a shared `security` module for input-path validation and key-based secret redaction, a circuit-breaker plus telemetry bolted onto `RuntimeControl`, hot-path clone/allocation reductions in the filter/sink/formatter, a large body of hand-rolled tests, and a set of honest status/reference docs. The approach is conservative — the perf refactors are semantics-preserving, redaction is on by default, and the docs are refreshingly candid about what the offline sandbox blocked and what the `<10%` overhead goal can't deliver. The FFI `// SAFETY:` comments and null guards are accurate and match the code they annotate.

Watch for: the circuit-breaker and telemetry (`record_error`/`record_success`/`safe_execute`) have **no production caller** — they are exported and unit-tested but never invoked by the live tracing pipeline, so the advertised "auto-disable after N consecutive errors" recovery does not actually fire in a running program (confirmed). Redaction is key-based only, so secrets embedded in free-form `Exception`/`RuntimeError`/`TypeError` `message` strings are not scrubbed (confirmed). CLI and dashboard redact using a hardcoded `Config::default()` rather than the env/loaded config, so `redact_key_patterns` customization and `XPLAINIT_*` settings are ignored on those paths (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Secret redaction is the strongest piece: a single choke point (`ExecutionEvent::redacted`) scrubs named maps and recurses into nested objects/arrays, and the single-value payload arms (return value, loop var, resumed value) close a real leak that the property test caught. The gap is scope — redaction keys off the *name* of a value, so a secret pasted into an exception message string flows through untouched, and the CLI/dashboard entry points bind `Config::default()` inline instead of honoring a configured policy.

The circuit-breaker is well-tested in isolation but disconnected from the framework it's meant to protect. Nothing in the tracing hot path calls `record_error`, `record_success`, or `safe_execute`, so consecutive real errors never accumulate and the breaker never trips outside its unit tests. The `panic = "abort"` limitation on `catch_unwind` is documented honestly, but the fallback it points to (the breaker) isn't wired in either.

The performance work is low-risk and correct: `location_ref()` borrows instead of cloning `SourceLocation`, the filters fall back to the exact `<unknown>` sentinel `location()` synthesized, `MemorySink` swaps `Vec::remove(0)` for `VecDeque::pop_front` (O(n)→O(1), FIFO preserved), and the formatter builds one buffer instead of collecting-and-joining. The `perf_regression` golden tests lock in byte-for-byte output so a semantics-changing revert fails.

Tests are meaningful and revert-sensitive rather than asserting static constants: the hand-rolled LCG property tests assert redaction idempotence and leak-freedom over generated inputs, and the FFI null-handle tests exercise the guarded error paths. Documentation is honest about offline-blocked tooling and the unmet overhead target.

### Redaction choke point and the nested-payload fix

The single-value payload arms are the real leak fix the property test surfaced. `FunctionExit.return_value`, `Return.value`, `AsyncTaskResume.resumed_with`, `LoopIteration.loop_var_value`, `TypeError.value`, and `DivisionByZero.numerator` carry no key of their own and can't be blanket-redacted, but they are recursed into via `redacted_nested` so a secret nested inside them still gets scrubbed; `test_redacts_secret_nested_in_return_value` and `test_redacts_secret_nested_in_loop_var_value` fail if that arm is reverted.

Redaction decides purely on the *key*, so the `message: String` on `Exception`, `RuntimeError`, and `TypeError` is never scrubbed. Error messages are a realistic place for secrets to land (`"auth failed: token=sk-..."`, a connection string with an inline password), and this is a live leak vector for a feature whose whole purpose is preventing secret egress. Either pattern-scan message strings or call the limitation out explicitly in SECURITY_AUDIT.md.

### CLI and dashboard bind a hardcoded default config

Both `load_events` implementations construct a local `Config::default()` and branch on its `redact_secrets`:

```rust
let config = Config::default();
if config.redact_secrets {
    Ok(redact_events(&events, &config.redact_key_patterns))
} else { Ok(events) }
```

Because the config is created inline rather than loaded from `Config::from_env` or passed in by the caller, any customization is silently dropped on these paths: a user who narrows or extends `redact_key_patterns`, or sets `XPLAINIT_*` env vars, gets the built-in defaults regardless. Redaction-on is preserved so this isn't a leak, but it makes the configuration surface a no-op exactly where events leave the process. Threading the loaded/env config through `load_events` would make the documented knobs real.

### Circuit-breaker is tested but not driven

`RuntimeControl` gains the breaker (`record_error` trips `enter_panic_mode` once the consecutive count hits `max_consecutive_errors`; `record_success` resets it) plus telemetry counters, and `safe_execute` feeds caught panics through `record_panic` + `record_error`. The unit tests cover the threshold trip, zero-disables-breaker, success-reset, and telemetry, asserting real state transitions.

The problem is reach: a repo-wide search finds no caller of `record_error`, `record_success`, `record_panic`, or `safe_execute` outside `control.rs` and the `pub use` re-export in `lib.rs`. The live tracing pipeline (capture → filter → processor → sink) never records framework errors or successes, so `consecutive_errors` stays at zero in any real run and the breaker only trips in its own tests. The module docs correctly explain that under the release `panic = "abort"` profile `catch_unwind` can't catch panics and that the breaker is the "primary, profile-independent recovery mechanism" — but that mechanism isn't connected to anything that produces errors in production. The honest fix is to either invoke `record_error`/`record_success` from the pipeline's fallible operations (and `safe_execute` around the capture callback), or to state in STATUS.md that the breaker is a public API surface not yet driven by the runtime, so the "auto-disables tracing" claim isn't read as active behavior.

### Performance refactors preserve semantics

The filters map `location_ref()`'s `None` to the literal `"<unknown>"`, which is exactly the `file` value `SourceLocation::unknown()` synthesized, so the filtering decision is unchanged while dropping a per-event `String` clone. One behavioral improvement worth noting: `MemorySink`'s move to `VecDeque::pop_front` (O(1) eviction, FIFO preserved) also removes a latent panic — `pop_front` on an empty deque is a no-op, whereas the old `Vec::remove(0)` would panic for a `MemorySink::new(0)`. `perf_regression.rs` pins the serialized JSON byte-for-byte and checks `location_ref()` against `location()` for every variant, so a semantics-altering revert fails rather than silently changing output.

### Test quality and FFI safety annotations

The property tests use a std-only deterministic LCG (no proptest dependency, consistent with the offline constraint) and assert invariants over generated events, including redaction idempotence and leak-freedom against a recognizable `SECRET_MARKER`. On the FFI side, every `// SAFETY:` comment matches its code — null/zero checked immediately above, `Box::from_raw`/`CString::from_raw` reclaiming exactly what `into_raw` produced, shared references only touching atomics or mutex-guarded state — and the new null-handle tests confirm the guarded error paths (`return 0` / null return) instead of dereferencing.
