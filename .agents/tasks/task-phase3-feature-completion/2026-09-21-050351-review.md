# Phase 3 Feature Completion — CLI, VS Code extension, advanced filters, async events, web dashboard (v1)

Phase 3 finishes the "feature completion" milestone (v0.3.0) with five deliverables layered onto the existing core engine: a clap-based `xplainit` CLI (`run`/`explain`/`analyze`/`report`), a source-only VS Code extension, five new `EventFilter` implementations, three async `ExecutionEvent` variants with a task-lifecycle tracker, and a new `xplainit-dashboard` crate — a hand-rolled tokio HTTP/SSE server with a no-build vanilla-JS frontend. The approach is consistently pragmatic about the sandbox: no new crates are pulled in, the frontend is `include_str!`-compiled static assets, and the CLI/README are honest that live tracing needs the per-language bindings rather than faking success. Most of the new Rust is well-tested at the unit level and the async/filter/dashboard logic is behaviorally sound.

Watch for: the VS Code extension silently drops the three new async event variants (confirmed) — they are absent from `trace.ts`, so `normalizeEvent` skips them, leaving the async feature invisible everywhere the extension renders a trace. The extension's default `recordTrace` flow shells out to `xplainit run <source>`, which for a source file prints human guidance text (not JSON), so the recorded file fails to parse (confirmed). The hand-rolled HTTP server reads a single 4096-byte chunk with no loop and no read timeout, so large requests are mis-parsed and idle connections pin a task (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The five new filters extend `EventFilter` cleanly and compose through the existing `CompositeFilter`. Edge cases are handled deliberately: `TimeRangeFilter` is inclusive on both open-endable bounds, `FrequencyFilter` is deterministic 1-in-N sampling via an atomic counter with error/type bypass, and `ValueFilter` distinguishes "no inspectable value" (pass-through, configurable) from "value present but non-matching" (drop). These are genuinely exercised by tests that would fail on revert.

The async story is split into a data model (three new `ExecutionEvent` variants) and a stateless reconstruction layer (`AsyncTaskTracker`) that keys timelines by `task_id`, so interleaved multi-task traces separate correctly and await/resume transitions flip `TaskState` as expected. Every downstream exhaustive `match` (explainer, formatter, dashboard aggregation, filter value extraction) adds meaningful arms rather than stubs, and the explainer produces per-verbosity prose. There is no explicit task-completion event; `Completed` is only reachable via `mark_completed`, which is a documented limitation.

The dashboard delegates all error reasoning to `xplainit_core::ErrorExplainer` and derives the call graph from enter/exit nesting with a stack (unmatched exits are ignored, siblings and nesting both tested). The HTTP layer is small and readable, but the connection reader is the weak point: one fixed-size read, no accumulation loop, no timeout.

The CLI is the strongest-documented piece: `run`/`explain` are explicit about which paths are wired (JSON rendering, static AST description, trace-driven explanation) versus not (live attach), and refuse to print success they did not achieve. The VS Code extension is solid TypeScript but has two integration gaps: it never learned about the async variants, and its record command assumes `xplainit run` emits JSON.

### Advanced filters: inclusive windows, deterministic sampling, value-presence semantics

The five filters slot into the existing `EventFilter` trait and compose through `CompositeFilter` with no changes to the trait. The design decisions worth noting are in the edge cases. `TimeRangeFilter` treats both bounds as inclusive and independently optional, so an open-ended window degenerates to accept-all; the tests pin the inclusive boundaries (`start` and `end` both captured) and both open-bound directions.

`FrequencyFilter` sidesteps the `&self` signature by counting through an `AtomicUsize`, giving deterministic 1-in-N sampling with no `rand` dependency. `fetch_add` returns the previous value so the first sampled event is count 1 and capture happens on multiples of the rate — the test asserts the exact `[false, false, true, ...]` sequence for rate 3, which would fail if the off-by-one were wrong. Errors and named event types bypass the counter entirely, and rate is clamped to `>= 1`. One behavioral note for callers: because `always_keep`/error bypass happens *before* `fetch_add`, kept events do not advance the sampling counter, so the 1-in-N cadence is measured over sampled events only, not all events — reasonable, but non-obvious.

`ValueFilter` makes a deliberate three-way distinction: an event with no inspectable value follows `pass_without_value` (default true, so unrelated events aren't silently dropped), while an event that *carries* values matches only if one of them satisfies the substring/type criteria. `values_of` enumerates the value-bearing variants explicitly; if new value-carrying variants are added later they must be added here too or they'll be treated as value-less. `render_value` sorts object entries for deterministic substring matching.

`PathFilter` reuses the simple-glob translation (`**`→`.+`, `*`→`[^/\\]+`, `?`→`.`) with exclusions winning over inclusions, and falls back to substring matching when the pattern isn't valid regex.

### Async event model and `AsyncTaskTracker`

The three new variants carry `task_id` separately from the event `id`, which is what lets `AsyncTaskTracker` reconstruct per-task timelines. The tracker is pure data/logic (no tokio, no `async` feature) and keys everything by `task_id`, so interleaved events from concurrent tasks land in the right timeline — the interleaving test spawns two tasks, interleaves start/await/resume, and asserts each task's ordered event list and final state independently. `record` maps start/resume→`Running` and await→`Awaiting`; first-seen id order is preserved for stable iteration.

The gap is completion: `TaskState::Completed` is only reachable through `mark_completed`, because there is no completion event variant. A task that runs to completion in a real trace therefore ends in `Running` or `Awaiting`. This is documented in the enum comment, so it's a known limitation rather than a bug, but it means "current state" is only fully accurate for suspended/running tasks.

The downstream wiring is complete and non-stubbed. The explainer's `explain_async_task_*` helpers produce distinct per-verbosity prose (task name/id, await target, resumed value), the formatter renders HTML for all three, and `error_explainer`'s exhaustive match falls through to `None` for async events (correct — they aren't errors). What's missing is a *consumer* of the tracker: neither the CLI, the formatter timeline, nor the dashboard call graph groups events by task, so the reconstruction the tracker performs isn't surfaced to a user anywhere yet.

### Dashboard call graph and error aggregation

Call-graph construction walks events with a stack: `FunctionEnter` pushes a node whose parent is the current stack top and whose depth is the stack length, `FunctionExit` pops. Unmatched exits are ignored (a pop on an empty stack is a no-op), so malformed traces don't panic — they just produce a flatter graph. Nesting, siblings, and JSON round-trip are all tested. Async events and errors are simply not `FunctionEnter`/`FunctionExit`, so they're skipped, which is consistent with a call graph but means an all-async trace yields an empty graph (the frontend shows "No function calls").

```
events: enter main, enter a, exit a, enter b, exit b, exit main
stack:  [0]        [0,1]   [0]     [0,2]   [0]    []
nodes:  main(0) -> children [a(1), b(2)]   (siblings under main)
```

Error aggregation delegates to `ErrorExplainer`: every event is fed to `track_event` for context, then error events are re-analyzed and rendered. `error_count` is derived from the label counts in `error_type_label`, so it counts only labelable errors — which today is every `is_error()` variant, but a future error variant added without a label arm would be counted as an error by `is_error()` yet omitted from `error_count`.

### Hand-rolled HTTP/SSE server: request reading is the weak point

Routing and response formatting are fine (query-string stripping, 405 for non-GET, 404 for unknown paths, correct multi-line SSE prefixing). The robustness gap is in `handle_connection`:

```rust
let mut buf = [0u8; 4096];
let n = stream.read(&mut buf).await?;   // single read, no loop
```

A request whose headers exceed 4096 bytes, or that arrives split across TCP segments, is parsed from a partial buffer — for the request *line* specifically this usually still works (the line is first), but there is no accumulation loop and, more importantly, no read timeout. An idle or slow client that opens a connection and sends nothing holds the spawned task open indefinitely (a slow-loris-style resource pin). Since the server binds `127.0.0.1` by default the exposure is limited, but `--bind` accepts any address, so a non-loopback deployment inherits the exposure. A bounded read-until-headers loop plus a per-connection read timeout would close both gaps.

On the client side, `app.js`'s `onmessage` handler feeds every SSE payload — including the terminal `{"done":true}` sentinel — into `addTimelineEntry`, which then appends a row with an empty type and location. The `onerror` handler separately closes the stream when the server hangs up, so reconnection is avoided, but the stray blank row remains. A one-line guard (`if (evt.done) return;`) fixes it.

### VS Code extension: solid TypeScript, two integration gaps

The TypeScript itself is careful (defensive `formatValue`, `escapeHtml`/`stripAnsi` and `enableScripts: false` in the webview); the two problems are integration-level.

First, `trace.ts` predates the async variants: `EventVariant`, `EVENT_TYPE_BY_VARIANT`, and `ERROR_VARIANTS` list only the pre-Phase-3 variants, and `normalizeEvent` returns `undefined` for any key not in `EVENT_TYPE_BY_VARIANT`. So a trace containing `AsyncTaskStart`/`Await`/`Resume` has those events silently dropped before they reach the timeline, hover, or error panel — the async feature is invisible in the editor. The core, CLI, and dashboard all handle these variants; only the extension's model was not updated.

Second, `recordTrace` shells out to `xplainit <recordCommand> <target>` and pipes stdout to the output `.json`, then calls `loadFromFile`. The default `recordCommand` is `run`. But `xplainit run` on a source file deliberately prints human-readable guidance ("Live tracing is not wired…"), not JSON — only `xplainit run <trace.json>` (an already-captured trace) emits renderable output, and even then it's the text report, not a JSON array. So the default record flow writes guidance text to a `.json` file and then throws in `parseTrace`. The CLI's honesty about live tracing is good; the extension just needs to not assume `run` yields a JSON trace (guard on content, or default to a JSON-emitting command/flow, or present the guidance to the user).

### CLI honesty about wired vs. not-wired paths

`run` and `explain` are explicit about which paths actually work. `run` renders a pre-captured `.json` trace (real) and, for source files, prints exactly which binding is needed rather than a fake "traced successfully." `explain` parses source via the core AST parser (real), explains trace events via `ExplanationGenerator` (real), and only declines the live-attach path. `report` correctly avoids double-wrapping the JSON formatter's already-array output while wrapping the per-event Text/HTML/Markdown formatters with header/footer. The integration tests drive the built binary directly (no `assert_cmd` dependency) and assert real output — division-by-zero analysis text, valid JSON round-trip, HTML document structure, and the not-wired message — so they'd fail on a revert.

### Test coverage

The new Rust is well covered at the unit level: filters assert exact boundary and sequence behavior, `AsyncTaskTracker` asserts interleaved separation and state transitions, the dashboard covers nesting/siblings/aggregation/timeline/serialization, and the CLI integration tests exercise the binary end to end.

Not tested: the async variants through the VS Code extension model (the very gap above — a test loading a trace with async events would have caught the omission); the `recordTrace` flow end to end (would have caught the `run`-emits-guidance mismatch); the HTTP server's behavior on oversized or slow/partial requests (no test drives `handle_connection` with a truncated or trickled request); and the SSE `{"done":true}` client handling. The TypeScript has no automated tests at all (acknowledged sandbox constraint — node/npm absent), so the two integration gaps went uncaught.
