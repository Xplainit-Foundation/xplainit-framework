# Phase 3 Feature Completion — verification of v1 fixes (v2)

Second-pass review after a round of fixes addressing the seven v1 findings. All five code-level gaps (VS Code async variants, `recordTrace` non-JSON guard, HTTP single-shot read, SSE `done` sentinel, dashboard `error_count`) are genuinely resolved in the code, and the two justified-deferral items (`TaskState::Completed`, tracker consumer) are handled — the completion deferral is documented with a concrete future-wiring plan, and the tracker now has a real consumer via `/tasks` + an "Async Tasks" panel. The new Rust tests exercise the fixed paths (bounded read loop, timeout, oversized rejection, `is_error`-derived count, per-task grouping) and 27 dashboard tests pass. No regressions to the normal small-GET path, the existing dashboard views, or the normal JSON record path were found; the TS additions are field-consistent with the Rust event model.

Watch for: nothing blocking. Two minor, non-blocking notes — the idle-client timeout test wraps `read_request_head` in its own 50ms timeout rather than driving `handle_connection`'s `READ_TIMEOUT`, so a regression that removed the timeout *in `handle_connection`* would not be caught by that test (confirmed); and the async event model still has no completion event, so a run-to-completion task reports `Running`/`Awaiting` (confirmed, and explicitly justified).

**Verdict**: APPROVED

## High-level view

The three async variants are now first-class in the VS Code model: `EventVariant`, `EVENT_TYPE_BY_VARIANT`, the `EventPayload` union (with `task_id`/`task_name`/`awaiting_on`/`spawned_from`/`resumed_with`), and `describeEvent` all carry them, and a new `eventLocation()` helper resolves `location ?? spawned_from` so `AsyncTaskStart` — which has no `location` field — indexes and reveals correctly. They are correctly kept out of `ERROR_VARIANTS`, matching `is_error()`.

`recordTrace` no longer pipes CLI stdout straight to a `.json`. It buffers stdout, runs `looksLikeTraceJson()` (must parse as a JSON array), and only then writes and loads; otherwise it surfaces the CLI's live-tracing guidance via the output channel and a warning. The normal JSON path is preserved.

The dashboard HTTP reader replaced the single 4096-byte read with `read_request_head()`: a bounded accumulation loop capped at 64 KiB (→ HTTP 431) that terminates on `find_head_end()` (CRLFCRLF or LFLF), all wrapped in a 15s `tokio::time::timeout`. Split-segment requests accumulate, oversized header blocks are refused, and an idle client is dropped instead of pinning a task.

`error_count` is now derived from `events.iter().filter(|e| e.is_error()).count()`, with a `debug_assert` that labelled counts never exceed the `is_error` total; `error_type_label` feeds only the `counts_by_type` breakdown. A future error variant lacking a label arm is still counted.

The `AsyncTaskTracker` finally has a consumer: `analysis::build_task_view()` groups lifecycle events by `task_id` and is served at `GET /tasks`, rendered by a hidden-by-default "Async Tasks" panel that stays hidden when a trace has no async events. `TaskState::Completed` remains reachable only via `mark_completed`, documented as a deliberate deferral with a plan to map a future `AsyncTaskComplete` in `record()`.

The SSE client skips any payload carrying `done` before `addTimelineEntry`, so the terminal `{"done":true}` sentinel no longer renders a blank row.

### Async variants in the VS Code model (v1 #1) — resolved

`trace.ts` now lists `AsyncTaskStart`/`AsyncTaskAwait`/`AsyncTaskResume` in `EventVariant` and maps them to `async_task_start`/`async_task_await`/`async_task_resume` in `EVENT_TYPE_BY_VARIANT`, so `normalizeEvent` no longer drops them. The `EventPayload` union gained `task_id`, `task_name`, `awaiting_on`, `spawned_from`, and `resumed_with`, and these field names match the Rust `ExecutionEvent` variants exactly (`AsyncTaskStart { task_id, task_name, spawned_from, .. }`, `AsyncTaskAwait { awaiting_on, location, .. }`, `AsyncTaskResume { resumed_with, location, .. }`), so serde's externally-tagged JSON deserializes into the right optional fields.

The location handling is the part that could silently regress: `AsyncTaskStart` has `spawned_from` instead of `location`, and the Rust `location()` accessor returns `spawned_from` for that variant. The new `eventLocation(event)` helper mirrors this with `payload.location ?? payload.spawned_from`, and `traceProvider.ts` uses it everywhere it previously read `payload.location` — `reindex` (byLocation indexing), `revealCursor` (jump-to-source), and `TimelineNode.toTreeItem` (tooltip). Miss any one and `AsyncTaskStart` would fall through as location-less; all three are converted. The variants are correctly absent from `ERROR_VARIANTS`, matching `is_error()`. TS is not compiler-checked in-sandbox (node/npm absent), so this rests on source consistency with the Rust model rather than a build.

### `recordTrace` non-JSON guard (v1 #2) — resolved

`recordTrace` now captures the child process stdout into a string and gates on `looksLikeTraceJson(stdout)` — which requires the trimmed output to start with `[` and `JSON.parse` to an array — before writing anything. On the common source-file case (`xplainit run` prints guidance, not JSON), it appends the guidance to the output channel and shows a warning telling the user to run under the per-language binding and export a JSON trace, then returns without writing. The normal path (stdout is a JSON array) still writes the file and calls `loadFromFile`. This closes the "guidance text written to a `.json` then throws in `parseTrace`" gap without breaking the real JSON flow.

### HTTP request reading (v1 #3) — resolved

```rust
let head = match tokio::time::timeout(READ_TIMEOUT, read_request_head(&mut stream)).await {
    Ok(result) => result?,
    Err(_elapsed) => return Ok(()),   // idle/slow client dropped
};
```

`read_request_head` accumulates 4 KiB reads into a `Vec`, returns `Complete` as soon as `find_head_end` locates `\r\n\r\n` (or `\n\n`), returns `Empty` on immediate EOF, and returns `TooLarge` once the buffer passes `MAX_REQUEST_HEAD_BYTES` (64 KiB) without terminating — which `handle_connection` turns into an HTTP 431. `find_head_end` handles both CRLFCRLF and bare LFLF. A normal small GET arrives with its terminator in the first read, so `find_head_end` matches immediately and the loop exits after one iteration — no regression to the fast path. Split-segment requests accumulate correctly (the `reads_head_split_across_reads` test splits a request at bytes 10/25 and asserts a `Complete` head).

The four new tests use a hand-rolled `ChunkReader` `AsyncRead` mock (no new dependency) and cover accumulation, empty connection, oversized rejection, and timeout. One fidelity gap: `read_timeout_fires_for_idle_client` wraps `read_request_head` in its own `timeout(50ms)` and asserts it elapses, rather than exercising `handle_connection`'s `timeout(READ_TIMEOUT, …)`. It proves the reader is cancel-safe under a timeout but would not fail if someone deleted the timeout wrapper in `handle_connection`. Low priority given the constant and the wrapper are both present and readable.

### Dashboard `error_count` (v1 #7) — resolved

`build_summary` now computes `error_count = events.iter().filter(|e| e.is_error()).count()` and keeps `error_type_label` solely for the `counts_by_type` grouping, with `debug_assert!(counts_by_type.values().sum() <= error_count)` documenting the invariant that a label subset can never exceed the authoritative total. A future error variant added to `is_error()` without a label arm is still counted in the total (it would only be missing from the per-type breakdown). The `error_count_tracks_is_error_not_labels` test asserts `error_count` equals the `is_error` count and, in the all-labelled case, equals the summed labelled counts — it would fail if the count reverted to summing labels only when a label arm is missing.

### `AsyncTaskTracker` consumer (v1 #6) — resolved

`analysis::build_task_view` builds an `AsyncTaskTracker::from_events`, iterates `timelines()` in first-seen order, and emits per-task `task_id`/`task_name`/`state`/`event_count`/`events`. It is routed at `GET /tasks` in `handle_connection` alongside the existing `/summary`, `/callgraph`, `/timeline`, and `app.js` fetches it and calls `renderTasks`, which keeps the `#tasks-panel` section (present in `index.html`, styled in `style.css`) hidden when there are no tasks and populates it otherwise. This is additive — it does not touch the summary/callgraph/timeline rendering — so existing views are unaffected. `task_view_groups_events_by_task` asserts two interleaved tasks separate with correct order, names, states, and counts; `task_view_is_empty_without_async_events` asserts a non-async trace yields `task_count == 0`.

### `TaskState::Completed` deferral (v1 #5) — justified

The enum doc comment now explains why there is no `AsyncTaskComplete` event: the language bindings that would emit async events are not wired in this environment, so a speculative completion event would be untested against a real runtime. `Completed` stays reachable only through `mark_completed` (for callers with out-of-band knowledge), and the comment records the intended future wiring — map a real completion event in `record()`. Downstream views report `Running`/`Awaiting` honestly rather than guessing. Reasonable deferral; nothing to change this pass.

### Regression scan

The normal small-GET path still completes in one read iteration; the record-flow change preserves the JSON path and only adds a guard; `/tasks` and the Async Tasks panel are additive and the panel defaults to hidden; the `error_count` change is a strict generalization of the previous value. No cross-cutting `match` was left non-exhaustive (workspace builds and clippy `-D warnings` are green per the orchestrator gate, re-confirmed here by a green `cargo test -p xplainit-dashboard` compile). No new dependencies were introduced.
