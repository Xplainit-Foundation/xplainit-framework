# Phase 2 runtime hooks: automatic event capture across five languages (v1)

Phase 2 wires each language binding to capture *real* runtime events instead of hand-fed static data. Python gets a corrected `sys.settrace` tracer (the headline fix is a depth-accounting bug that used to wedge tracing off permanently); C/C++ gets a `-finstrument-functions` shim that resolves symbols via `dladdr` and forwards to the FFI; Java gets a JVMTI agent driving process-wide recording statics through JNI; Go gets a defer-based manual tracer over the C FFI; Node gets a wrapper-based tracer with an injectable backend. Every language except Node ships a build-gate script that runs an instrumented program and asserts non-empty, correctly-named events — these are genuine end-to-end gates, not tautologies. I reproduced all of them in-sandbox and they pass.

Watch for: (1) the Node native JS→Rust round-trip is **unverified** in-sandbox because node/npm are absent — only the JS capture logic is tested against a mock (author-documented, *confirmed*); (2) Java exception `error_type` is the raw JVMTI signature `Ljava/lang/ArithmeticException;` with an empty message, and Java/Go carry no line numbers or argument values (author-documented, *confirmed*); (3) the C example's second-batch statistics report `errors=0` even though a `DivisionByZero` was captured in the first batch, because the re-run subset deliberately excludes the error path — mildly misleading presentation, not a data bug (*confirmed*).

**Verdict**: APPROVED

## High-level view

The depth-accounting fix is the substantive change and it is correct. Depth is now maintained unconditionally in `_handle_call`/`_handle_return`; `max_depth` and `sampling_rate` only gate whether an event is *recorded*, tracked per-frame in a `recorded_frames` set so enter/exit stay balanced. The old code gated `_should_trace` on depth, so once depth passed `max_depth` the matching returns were filtered too, depth ratcheted upward, and tracing wedged off for the thread. I confirmed the failure mode by re-introducing the old gate: a top-level call issued after deep recursion is silently dropped. The regression test pins exactly this.

Each language captures real events end to end through the shared `xplainit_core` event store. C uses compiler instrumentation + `dladdr`; Java uses a JVMTI agent that funnels MethodEntry/Exit/Exception through JNI into a process-wide `OnceLock` runtime; Go uses an explicit `defer`-based `Trace` helper (Go has no settrace equivalent, honestly scoped as such); Node wraps functions and forwards to an injectable backend. All FFI recording paths are gated on a real `AtomicBool` enabled flag and null-handle-safe.

The API surface is consistent across bindings: enter/exit/exception recording plus `get_events`/`get_statistics`, both of which *drain* the store. The examples and tests are written to read JSON before statistics to account for this draining, and the C example re-runs a call subset to repopulate — a workaround that produces the `errors=0` statistics quirk noted above.

The honesty scoping is the part the user cares about, and it holds up: the Node round-trip limitation, and the Java/Go line-number and argument-value gaps, are documented in the respective READMEs and in `task.json`, and match what actually builds and runs here. No completion claim I checked is overstated relative to sandbox reality.

### The depth-accounting fix and why it holds under sampling/generators/async

The bug was structural: `_should_trace` returned `False` whenever `_get_depth() > max_depth`, and it is consulted for both `call` and `return`. Past `max_depth` the returns were filtered, their decrement never ran, and depth climbed monotonically until every subsequent frame was above the ceiling — tracing was dead for the rest of the thread's life. The fix splits the two responsibilities cleanly: `_handle_call` always does `depth += 1` and `_handle_return` always does `depth = max(0, depth-1)` for any frame that passed the identity filter, while `max_depth` and `sampling_rate` only decide recording. The recording decision is memoized in a per-thread `recorded_frames` set keyed on `id(frame)`, and the matching return records iff the frame id is present. This is what keeps `FunctionEnter`/`FunctionExit` balanced regardless of the recording gates.

I verified the failure and the fix by monkeypatching the old depth gate back into `_should_trace` and running the regression scenario (`deep(30)` with `max_depth=5`, then a fresh top-level `simple_after()`): with the old gate, `simple_after` is not captured and depth is stuck; with the shipped code it is captured and depth returns to 0. The regression test asserts exactly that, so it would fail on revert — it is a real behavioral test.

The generator and async cases are worth calling out because `sys.settrace` emits a paired `call`/`return` on every resume/suspend (yield, await). Since the fix balances every counted call with its return, these paired events net to zero and depth returns to 0 after draining a generator or after `asyncio.run`. The tests confirm both, and confirm that asyncio's event-loop internals are correctly excluded as stdlib so only the user coroutine body is traced.

One subtlety with sampling: because the record decision is stored per-frame and the frame object stays alive between its call and return, `id(frame)` is stable across the pair, so a sampled-out call cannot leave a dangling exit. Sampling is deliberately applied in `_handle_call`, never in `_should_trace`, precisely so the call and return of one frame get the same answer.

### C instrumentation: real symbol capture, single-lock serialization

```
compiled with -finstrument-functions
   │  every fn enter/exit
   ▼
__cyg_profile_func_enter/exit (trace.c, no_instrument_function)
   │  dladdr(this_fn) → symbol name
   ▼
xplainit_on_function_enter/exit (FFI, gated on AtomicBool)
   │  lock(runtime) → event_store().record(...)
   ▼
xplainit_core event store  ──drain──▶ get_events / get_statistics
```

The shim is correctly marked `no_instrument_function` throughout, so it does not recurse into itself, and it null-checks the global handle before every callback. Symbol resolution falls back to `"<unknown>"` when `dladdr` fails. The gate script compiles the example with `-finstrument-functions -rdynamic -ldl`, runs it, and asserts the presence of `factorial`, `add`, `multiply`, `calculate_something`, and the `DivisionByZero` error path — I ran it and got 16 real events including 5-deep `factorial` recursion.

Two honest limitations show through in the captured data: file is always `"<c>"` and line is `0` for enter/exit (the instrumentation callback has only the function address, not a source location), while the manually-reported exception *does* carry `__FILE__`/`__LINE__`. The performance note: every traced enter/exit locks the runtime `Mutex` and does a `dladdr` lookup, so in a multithreaded program all traced calls serialize on one lock. That is acceptable for a demo/gate but is the overhead ceiling to disclose before pointing anyone at C tracing for hot code.

### Java JVMTI agent → JNI → process-wide runtime

The agent (`agent.c`) does not record directly; it resolves `io.xplainit.Xplainit.agentOnMethodEnter/Exit/Exception` in `VMInit` and calls them via JNI, so all recording flows through the same tested Rust path into a process-wide `OnceLock<JavaRuntime>`. Two safety mechanisms matter and are present: a thread-local `g_in_callback` guard prevents the bridge's own JNI calls from re-triggering MethodEntry infinitely, and a class-signature prefix filter (`Lio/xplainit/examples/` by default) keeps the agent from recording the entire JDK. All JVMTI-allocated strings are `Deallocate`d and all JNI local refs are deleted; `ExceptionCheck`/`ExceptionClear` wraps each upcall. The gate runs `BasicExample` under `-agentpath` and asserts `doubleValue`, `fibonacci` (with recursion), and `divide` plus the thrown exception — I ran it and saw all of them.

The fidelity gap is the exception representation: `error_type` is the raw signature `Ljava/lang/ArithmeticException;` and the message is hard-coded empty (`NewStringUTF(jni, "")`), because the callback resolves only the exception's class signature, not its message. Demangling the signature and reading `getMessage` via JNI would make the exception events usable; today they identify the type only in raw JVM form. Line numbers are `0` and arguments are absent, consistent with the documented scope.

### Go: explicit defer tracing, correctly scoped as manual

Go has no `sys.settrace` analogue, and the binding says so plainly rather than pretending otherwise. `Trace(name, file, line)` records the enter immediately and returns a closure that records the exit, meant to be used as `defer x.Trace(...)()`. Every CGO string is freed with `defer C.free`, and every method null-checks the handle. The tests link against the release `libxplainit_c` and assert real captured events including factorial recursion and a division-by-zero path; they pass here. Arguments and line fidelity are the caller's responsibility since this is a manual API.

### Node: injectable backend, async settlement, unverified native path

The wrapper tracer captures real argument values, return values, and thrown/rejected errors, forwarding to a backend implementing `onFunctionEnter/onFunctionExit/onException`. Async is handled by recording exit/exception when the returned promise settles, and a `_recording` re-entrancy flag prevents a backend that itself calls traced code from looping. The 44-assertion suite exercises sync, async-resolve, and async-reject paths against a pure-JS mock and passes under bun.

The gap the user must not lose sight of: this verifies the *JS capture logic only*. The production backend is the Neon N-API addon, which bun cannot load and which needs `npm run build` — and node/npm are absent in this sandbox. So the JS→Rust round-trip is genuinely unverified here. The README states this directly (only bun 1.2.14 available, prebuilt addon gives `invalid ELF header` under bun), so the claim is scoped honestly, but "Task 2.2 done" should carry that asterisk until someone runs it on real Node.

### Store-draining contract

Both `get_events` and `get_statistics` drain the underlying store in `xplainit_core`. This is a shared behavior the examples must respect: the C example dumps JSON first, then re-runs a subset to repopulate before calling statistics; the Java/Go tests read in a compatible order. This is where the C `errors=0` summary comes from — the repopulating subset (`add`, `calculate_something`, `factorial`) deliberately omits the error path, so the second statistics batch legitimately has zero errors even though the first-batch JSON contains the `DivisionByZero`. The summary line invites misreading and would be clearer if it either re-ran the error path or labeled itself as a partial subset.
